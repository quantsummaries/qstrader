# `qstrader.execution`

## Overview

The `qstrader.execution` package provides the **order representation and execution management layer** for QSTrader. It handles the lifecycle of trade orders generated by portfolio construction and bridges the gap between target portfolio rebalance requests and brokerage execution.

The package consists of two main abstractions:

- **Order Data Container:** `Order` represents an explicit order to buy or sell a specified quantity of an asset.
- **Execution Management:** `ExecutionHandler` routes rebalance orders through an execution algorithm and submits them to the broker.
- **Execution Algorithms (`execution_algo`):** `ExecutionAlgorithm` and its concrete implementation `MarketOrderExecutionAlgorithm` define strategies for transforming or timing orders before submission.

## Core classes

### `Order`

**Source:** `qstrader/execution/order.py`

`Order` is a data class representing an order sent to a brokerage for execution.

#### Constructor

```python
Order(
    dt: pd.Timestamp,
    asset: Asset,
    quantity: int,
    commission: float=0.0,
    order_id: str|None=None
)
```

#### Parameters

- `dt: pd.Timestamp` — the creation datetime of the order.
- `asset: Asset` — the asset or asset symbol to transact.
- `quantity: int` — the integer unit size to transact (positive = buy / long, negative = sell / short).
- `commission: float = 0.0` — optional known commission override.
- `order_id: str | None = None` — optional explicit unique identifier. If `None`, a random hex UUID (via `uuid.uuid4().hex`) is generated automatically.

#### Attributes

- `created_dt: pd.Timestamp` — creation timestamp.
- `cur_dt: pd.Timestamp` — current timestamp (tracks modification time).
- `asset: Asset` — target asset.
- `quantity: int` — trade quantity.
- `commission: float` — commission cost.
- `direction: float` — derived direction (`+1.0` for buy/long, `-1.0` for sell/short) computed via `np.copysign(1, quantity)`.
- `order_id: str` — unique order identifier string.

#### Internal methods

- `_set_or_generate_order_id(order_id: str|None=None) -> str` — returns `order_id` if supplied, otherwise generates a UUID hex string.
- `_order_attribs_equal(other: Order) -> bool` — compares non-ID attributes (`created_dt`, `cur_dt`, `asset`, `quantity`, `commission`, `direction`) for equality testing.
- `__repr__() -> str` — string representation detailing created datetime, asset, quantity, commission, direction, and order ID.

### `ExecutionHandler`

**Source:** `qstrader/execution/execution_handler.py`

`ExecutionHandler` receives raw rebalance orders from portfolio construction, passes them through an `ExecutionAlgorithm`, and (if enabled) submits them to the `Broker`.

#### Constructor

```python
ExecutionHandler(
    broker: Broker,
    broker_portfolio_id: str,
    universe: Universe,
    submit_orders: bool=False,
    execution_algo: ExecutionAlgorithm|None=None,
    data_handler: BacktestDataHandler|None=None
)
```

#### Parameters

- `broker: Broker` — the broker instance where orders are submitted.
- `broker_portfolio_id: str` — the sub-portfolio ID receiving the orders.
- `universe: Universe` — active asset universe.
- `submit_orders: bool = False` — toggle controlling whether orders are submitted to `broker` or silently discarded.
- `execution_algo: ExecutionAlgorithm | None = None` — execution algorithm instance applied to rebalance orders.
- `data_handler: BacktestDataHandler | None = None` — optional data handler for price or market-data queries needed by execution strategies.

#### Methods

##### `_apply_execution_algo_to_rebalances(dt: pd.Timestamp, rebalance_orders: list[Order]) -> list[Order]`

Passes `rebalance_orders` to `self.execution_algo(dt, rebalance_orders)` and returns the resulting orders.

##### `__call__(dt: pd.Timestamp, rebalance_orders: list[Order]) -> None`

Executes the order pipeline:
1. Applies the execution algorithm via `_apply_execution_algo_to_rebalances`.
2. If `self.submit_orders` is `True`, iterates through the final orders and submits each to `self.broker.submit_order(self.broker_portfolio_id, order)`, followed by updating the broker state with `self.broker.update(dt)`.

## Execution algorithms subpackage (`execution_algo`)

The `qstrader.execution.execution_algo` package contains abstract and concrete execution strategies.

### `ExecutionAlgorithm`

**Source:** `qstrader/execution/execution_algo/execution_algo.py`

Abstract base class for order execution algorithms.

```python
class ExecutionAlgorithm(object):
    @abstractmethod
    def __call__(self, dt: pd.Timestamp, initial_orders: list[Order]) -> list[Order]:
        raise NotImplementedError("Should implement __call__()")
```

#### Contract

Implementations take the timestamp `dt` and a list of target rebalance orders (`initial_orders`), returning a transformed or scheduled list of orders to send to the broker.

---

### `MarketOrderExecutionAlgorithm`

**Source:** `qstrader/execution/execution_algo/market_order.py`

Default pass-through execution strategy that leaves rebalance orders unmodified as standard market orders.

#### Method

```python
def __call__(self, dt: pd.Timestamp, initial_orders: list[Order]) -> list[Order]:
    return initial_orders
```

Returns `initial_orders` without modification.

## How execution is used in QSTrader

Execution is wired into the system execution pipeline within `QuantTradingSystem` (`qstrader/system/qts.py`):

```text
QuantTradingSystem.__call__(dt)
 ├── 1. PortfolioConstructionModel(dt) -> rebalance_orders
 └── 2. ExecutionHandler(dt, rebalance_orders)
      ├── MarketOrderExecutionAlgorithm(dt, rebalance_orders) -> final_orders
      └── if submit_orders:
           for order in final_orders:
               Broker.submit_order(portfolio_id, order)
               Broker.update(dt)
```

In standard backtests constructed with `BacktestTradingSession`, `QuantTradingSystem` initializes `ExecutionHandler` with `MarketOrderExecutionAlgorithm` and `submit_orders=True`.

---

## Design notes and limitations

- **Pass-through default:** the default algorithm (`MarketOrderExecutionAlgorithm`) passes orders through instantly without slicing or delaying.
- **Custom execution algorithms:** custom strategies (e.g. TWAP, VWAP, limit orders, or price-slice algorithms) can be created by subclassing `ExecutionAlgorithm`.
- **Order submission toggle:** `submit_orders=False` allows testing portfolio construction order generation without modifying broker state or triggering trades.
- **Immediate broker update:** `ExecutionHandler` calls `broker.update(dt)` immediately after each `submit_order` call during submission.

## Quick reference

| Class | Module | Purpose | Key API |

## Minimal usage examples

### Creating an Order

```python
import pandas as pd
import pytz
from qstrader.execution.order import Order

dt = pd.Timestamp('2024-01-03 14:30:00', tz=pytz.UTC)
order = Order(dt, asset='EQ:SPY', quantity=100)

print(order)
# Order(dt='2024-01-03 14:30:00+00:00', asset='EQ:SPY', quantity=100, commission=0.0, direction=1.0, order_id='...')
```

### Executing rebalance orders via ExecutionHandler

```python
from qstrader.execution.execution_handler import ExecutionHandler
from qstrader.execution.execution_algo.market_order import MarketOrderExecutionAlgorithm

execution_handler = ExecutionHandler(
    broker=broker,
    broker_portfolio_id='000001',
    universe=universe,
    submit_orders=True,
    execution_algo=MarketOrderExecutionAlgorithm(),
    data_handler=data_handler
)

# Submit rebalance orders to the broker
execution_handler(dt, rebalance_orders)
```

## Summary

`qstrader.execution` connects portfolio construction to broker execution. It encapsulates trade details in `Order` objects and provides an extensible `ExecutionHandler` pipeline using pluggable `ExecutionAlgorithm` strategies.
